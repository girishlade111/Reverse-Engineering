QUALITY STANDARDS
========================================================================
Enterprise Reverse Engineering Prompt Framework
Version: 3.0

========================================================================
QUALITY DIMENSIONS
========================================================================

Every artifact generated by this framework is evaluated against
the following dimensions:

1. ACCURACY (Weight: 25%)
   - Every claim is supported by code evidence
   - Technical details are correct
   - No factual errors
   - No hallucinated features or behaviors

2. COMPLETENESS (Weight: 20%)
   - All required artifact sections are present
   - All files/features in scope are covered
   - No significant gaps in analysis
   - Edge cases are documented

3. CLARITY (Weight: 15%)
   - Language is precise and unambiguous
   - Structure is logical and navigable
   - Terminology is consistent throughout
   - Diagrams are well-labeled and explained

4. DEPTH (Weight: 15%)
   - Analysis goes beyond surface-level descriptions
   - Design rationale is explained
   - Trade-offs are documented
   - Implications are discussed

5. ORGANIZATION (Weight: 10%)
   - Information is structured hierarchically
   - Related content is grouped together
   - Navigation is intuitive
   - Cross-references are provided

6. CONSISTENCY (Weight: 10%)
   - Terminology is uniform across all artifacts
   - Diagram styles are consistent
   - Documentation format is standardized
   - Naming conventions match the source code

7. USABILITY (Weight: 5%)
   - Documentation is actionable
   - Developers can use it to understand the system
   - Architects can use it for decision-making
   - Newcomers can use it for onboarding

========================================================================
QUALITY SCORING RUBRIC
========================================================================

SCORE 5 (Excellent):
- Exceeds standard for the dimension
- No errors or omissions
- Provides additional insight beyond requirements

SCORE 4 (Good):
- Meets standard fully
- Minor issues that do not affect understanding
- All requirements met

SCORE 3 (Adequate):
- Meets minimum standard
- Some gaps or unclear sections
- Requirements met but not exceeded

SCORE 2 (Below Standard):
- Falls short of minimum requirements
- Notable gaps, errors, or unclear sections
- Requires revision

SCORE 1 (Poor):
- Does not meet requirements
- Significant errors or omissions
- Must be rewritten

========================================================================
MINIMUM ACCEPTABLE QUALITY
========================================================================

All artifacts must achieve:
- Overall weighted score >= 4.0
- No single dimension below 3.0
- Accuracy dimension >= 4.0
- No evidence of hallucination
- All required sections present

========================================================================
COMMON DEFECTS TO AVOID
========================================================================

DEFECT 1: VAGUE LANGUAGE
Avoid: "The system handles various types of requests."
Prefer: "The system handles three request types: HTTP REST,
WebSocket, and gRPC, dispatched via the ApiGateway class in
`src/gateway/router.ts:12`."

DEFECT 2: UNSUPPORTED CLAIMS
Avoid: "This is a microservice architecture."
Prefer: "The repository contains 12 separate services, each with
its own `package.json` and Dockerfile, organized in the
`services/` directory. This indicates a microservice architecture."

DEFECT 3: MISSING CONTEXT
Avoid: "The `process` function transforms the data."
Prefer: "The `process` function in `src/pipeline/processor.ts:45`
accepts a `RawRecord` object, validates it against the schema in
`src/schemas/record.json`, enriches it with geo-location data,
and returns a `ProcessedRecord` object."

DEFECT 4: INCOMPLETE DIAGRAMS
Avoid: A diagram with no explanation.
Prefer: A diagram with a descriptive caption, legend for any
symbols or colors, and a narrative explanation following it.

DEFECT 5: INCONSISTENT TERMINOLOGY
Avoid: Switching between "service," "module," and "component"
for the same concept.
Prefer: Define each term on first use and use it consistently.

========================================================================
QUALITY VERIFICATION PROCESS
========================================================================

STEP 1: Self-Review
Before finalizing any artifact, review it against all quality
dimensions. Score it yourself. Document any known issues.

STEP 2: Cross-Reference Check
Verify that every claim about a file can be traced to the actual
file content. Check that cross-references between artifacts are
accurate.

STEP 3: Completeness Check
Compare the artifact against the required sections list for its
type. Verify nothing was omitted.

STEP 4: Consistency Check
Verify terminology, formatting, and style are consistent across
all artifacts generated so far.

STEP 5: Usability Check
Read the artifact as if you were a developer new to the system.
Does it provide the information needed to understand the system?
