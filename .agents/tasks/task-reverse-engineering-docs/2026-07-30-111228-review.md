# Complete reverse-engineering documentation for a prompt framework repository

This changeset introduces a 15-file documentation suite (`docs/`) that reverse-engineers the repository itself, a collection of 10 AI prompt framework variants designed to guide LLMs through structured software analysis. The documentation adapts conventional reverse-engineering phases (architecture reconstruction, data flow analysis, etc.) to document prompt template structure, orchestration logic, and agent workflow rather than functions and APIs. File counts are verified (303 files accounted for), cross-references between phases resolve correctly, and Mermaid diagrams use valid syntax. The documentation is thorough and would allow someone unfamiliar with the repository to understand its purpose, architecture, and extension points.

Watch for: The rebuild guide (Phase 9) describes a different pipeline than the architecture documentation (Phases 4-6), conflating the documentation output phases (1-10) with the Hermes variant's execution pipeline (9 phases, 36 prompts) [confirmed]. Phase 10's self-audit contains a stale "332 total" figure that contradicts the verified 303-file count elsewhere [confirmed]. Directory names in Phase 2 use regular hyphens where the filesystem uses em-dashes, which is documented as intentional but creates broken paths if used for programmatic navigation [confirmed].

**Verdict**: APPROVED

## High-level view

The documentation is structured as a complete 10-phase reverse-engineering run where each phase builds on the prior phase's output. Phase 1 establishes the repository map (10 variants, 303 files, Markdown-only stack). Phase 2 catalogs every file with verified counts. Phase 3 treats individual prompts as code units with a canonical 7-section template. Phases 4-6 reconstruct the architecture, diagram it, and analyze the agentic workflow. Phases 7-10 cover tech stack, conditional sections, rebuild guide, and self-audit. The inter-phase cross-references form a dense link graph that resolves correctly across all 15 files.

The primary structural flaw is in the rebuild guide, which describes the wrong pipeline. Phases 4-6 consistently document the Hermes variant's 9-phase, 36-prompt execution model with Phase 5 (AI) and Phase 9 (rebuild) as conditional. The rebuild guide instead describes a 10-phase, single-prompt-per-phase model with Phase 6 (AI) and Phase 8 (conditional docs) as optional, and uses a different 7-section template structure. This appears to conflate the documentation output structure (the 10 documentation phases being produced) with the Hermes variant's internal execution architecture.

Phase 10 (validation QA) marks all 6 self-audit items as passing, but the "332 total" reference and the pipeline inconsistency described above would both fail under strict audit criteria.

## Rebuild guide pipeline identity crisis

The architecture documentation (system-design.md, module-map.md, working-logic.md, diagrams.md, ai-agent-workflow.md) presents a consistent picture: the Hermes variant runs 36 prompts across 9 phases, with Phase 5 (AI/Automation Analysis, P16-P20) being conditional on AI pattern detection and Phase 9 (Rebuild Package, P35-P36) being optional. The module-map.md includes a detailed DAG, parallelization batches, and critical path analysis based on this model.

The rebuild guide (Phase 9) describes a fundamentally different architecture:

```
Rebuild guide model:
  10 phases, 1 prompt per phase, flat numbering (PROMPT_01 through PROMPT_10)
  Conditional: Phase 6 (AI code), Phase 8 (APIs/DBs)
  Template: Objective, Inputs, Execution Instructions, Output Format,
            Quality Gates, Conditional Logic, Continuation Trigger

Architecture docs model:
  9 phases, 36 prompts total (2-6 per phase), hierarchical (Phase N/PROMPT_NN_Name.md)
  Conditional: Phase 5 (AI patterns), Phase 9 (rebuild requested)
  Template: MISSION, PREREQUISITES, SYSTEM PROMPT, EXECUTION INSTRUCTIONS,
            OUTPUT SPECIFICATION, QUALITY GATE, HANDOFF
```

Someone following the rebuild guide would produce a variant that does not match the architecture described in the rest of the documentation. The rebuild guide appears to describe the documentation output structure (this very docs/ folder follows 10 phases with the same numbering and conditional logic) rather than the Hermes variant's internal execution model.

## File count verification and Phase 10 arithmetic

Phase 2 correctly accounts for all 303 files with a per-directory verification table that sums exactly to 303. These match the actual filesystem count (verified: `find . -not -path './.git/*' -not -path './.agents/*' -not -path './docs/*' -type f | wc -l` returns 303).

Phase 10, however, states: "accounting for the documented total of 303 files (332 total minus internal/generated files)." The 332 figure has no basis in the current repository state. The total file count including docs/ and .agents/ is 324, not 332. The 332 appears to be a stale initial estimate from the task briefing (the FEAT-001.json findings explicitly note "Repository contains 303 files (not 332 as initially estimated)"). The parenthetical should be removed.

## Directory name normalization

The actual Hermes variant uses em-dashes in directory names (`Phase 1 — Discovery/`). The documentation normalizes these to regular hyphens in the repository tree (01-repository-intelligence.md) and drops the descriptive suffix entirely in the file path tables (02-file-folder-analysis.md references `Phase 1/PROMPT_01_Repository_Scan.md`). The FEAT-001.json notes this is intentional per OUTPUT_RULES. The consequence: the "File" column in Phase 2's tables contains paths that do not resolve on disk. A reader using these paths for shell navigation or scripting would encounter "No such file or directory" errors.
