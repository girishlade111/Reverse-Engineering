\# PROMPT DESIGN GUIDE: REVERSE ENGINEERING FRAMEWORK



\## 1. DESIGN PRINCIPLES



\### 1.1 Core Principles



\*\*PRINCIPLE 1: COMPLETENESS FIRST\*\*

Every prompt must ensure 100% coverage. No component, relationship, or behavior can be omitted.



\*\*PRINCIPLE 2: VERIFICATION OVER ASSUMPTION\*\*

Every fact must be verified from source code. Assumptions must be explicitly marked.



\*\*PRINCIPLE 3: PRECISION OVER BREVITY\*\*

Technical accuracy is more important than concise output. Never simplify complex logic.



\*\*PRINCIPLE 4: TRACEABILITY\*\*

Every statement in documentation must be traceable back to source code.



\*\*PRINCIPLE 5: CONSISTENCY\*\*

Terminology, formatting, and structure must be consistent across all outputs.



\*\*PRINCIPLE 6: MAINTAINABILITY\*\*

Documentation must be structured for long-term maintenance.



\## 2. DESIGN PATTERNS



\*\*PATTERN 1: Hierarchical Analysis\*\*

Repository → Folders → Files → Modules → Classes → Functions → Code Blocks

Analyze from top-down, then verify bottom-up.



\*\*PATTERN 2: Relationship-First\*\*

Identify relationships before documenting individual components.



\*\*PATTERN 3: Dependency Graph First\*\*

Build complete dependency graphs before detailed analysis.



\*\*PATTERN 4: Iterative Refinement\*\*

1\. Pass 1: Structural overview (files, folders, modules)

2\. Pass 2: Relationship mapping (dependencies, imports, calls)

3\. Pass 3: Behavioral analysis (execution flows, state transitions)

4\. Pass 4: Detailed documentation (functions, classes, logic)



\## 3. PROMPT ARCHITECTURE



\### 3.1 Modular Design

Each prompt module must:

\- Have a single, clear responsibility

\- Be independently executable

\- Accept well-defined inputs

\- Produce well-defined outputs

\- Be composable with other modules



\### 3.2 Input/Output Contracts



\*\*Input Contract:\*\*

\- Repository path or code content

\- Previous analysis results (for dependent prompts)

\- Configuration options

\- Analysis depth settings



\*\*Output Contract:\*\*

\- Structured data (JSON or YAML)

\- Human-readable documentation (Markdown)

\- Diagrams (Mermaid, PlantUML, or SVG)

\*\*Rule:\*\* Complex logic must be documented as-is, not simplified.

Always analyze structure (files, folders, modules) before behavior.



\*\*RULE 2: DEPENDENCIES BEFORE IMPLEMENTATION\*\*

Always map dependencies before analyzing implementation.



\*\*RULE 3: ENTRY POINTS BEFORE INTERNAL LOGIC\*\*

Always identify and trace entry points before internal functions.



\*\*RULE 4: TOP-DOWN THEN BOTTOM-UP\*\*
